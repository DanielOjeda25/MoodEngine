# F2H68 — Auto-ragdoll por impacto (ContactListener + sensor bodies)

**Estado:** Cerrado con **bug conocido** (2026-05-19)
**Tag:** `v1.55.0-fase2-hito68`
**Predecesores:** F2H66 (ragdolls), F2H67 (vehicles).
**Sucesor planeado:** **F2H69** — Pipeline glTF multi-node + debug del trigger NPC + reemplazar sedan Kenney por modelo correctamente armado.

---

## Motivación

Pregunta del dev al probar F2H67: *"si un vehiculo, si choca un NPC con trigger ragdoll, este caera o sentira el impacto?"*. Respuesta inicial: no. La activación de `RagdollComponent` era 100% manual via Lua (`ragdoll.enable`) o C++. No existía `JPH::ContactListener` registrado en `PhysicsWorld`. Los únicos "eventos" físicos eran overlaps de `TriggerVolumeComponent` (sensores OBB, no contactos reales).

Este hito **monta la infra completa** para auto-ragdoll por impacto siguiendo el standard industry (Unity `Collider.isTrigger` / Unreal `Overlap` / Jolt `ContactListener`). El sample concreto (atropellar NPC con el Banshee) **NO funciona end-to-end** — el ContactListener probablemente recibe el contact pero el drain no transiciona el NPC. Se documenta como bug conocido a resolver en F2H69.

## Diseño (infra)

### Mapa `BodyID → entt::entity`

`PhysicsWorld::Impl::bodyToEntity` (`std::unordered_map<u32, u32>`). Los sistemas dueños lo mantienen via `registerBodyEntity` / `unregisterBodyEntity`:

| Sistema | Cuándo registra |
|---|---|
| `EditorScene::updateRigidBodies` + `PlayerApplication_Frame::updateRigidBodies` | Después de `createBody` para una entity con `RigidBodyComponent` |
| `VehicleSystem::tick` (materialize lazy) | Después de `createVehicle`, registra el chassis body |
| `RagdollSystem::tick` (transición → Ragdolling) | Después de `createRagdoll`, registra cada part body via `ragdollBodyIds()` (todos mapean al mismo entity owner) |

Cleanup automático: `destroyBody` / `destroyVehicle` / `destroyRagdoll` erase la entrada del map. Idempotente.

### `physics_internal::ContactListener`

Vive en `PhysicsWorld_Internal.h` + `PhysicsWorld_Impact.cpp`. Override de `JPH::ContactListener::OnContactAdded`:

1. Skip si ambos bodies no son Dynamic (sin movimiento posible).
2. Lee `body1.GetLinearVelocity() - body2.GetLinearVelocity()` (vrel) y `manifold.mWorldSpaceNormal` (apunta de body1 a body2 por convención Jolt).
3. `closingSpeed = vrel.Dot(normal)`. Si < `impactSpeedThreshold` (default 4 m/s) → return.
4. Calcula `impulseMag = closingSpeed * impactImpulseFactor` (default 0.3 = arcade GTA SA feel).
5. Push 2 eventos a `Impl::impactQueue` (uno por body): `{victimBodyId, ±normal*impulseMag, closingSpeed}`. Mutex defensivo.

**Por qué no muta el world directamente**: Jolt prohíbe crear/destruir bodies o cambiar state dentro del callback. Solo permite modificar `ContactSettings`. Encolamos para drenar fuera.

### Drain en `RagdollSystem::tick`

Antes del materialize lazy:

```cpp
auto events = physicsWorld.drainImpactEvents();
for (const auto& ev : events) {
    const u32 entHandle = physicsWorld.entityOfBody(ev.victimBodyId);
    Entity victim = scene.entityFromHandle(...);
    if (!victim.hasComponent<RagdollComponent>()) continue;
    auto& rd = victim.getComponent<RagdollComponent>();
    if (rd.state != RagdollComponent::State::Animated) continue;
    rd.state        = RagdollComponent::State::Ragdolling;
    rd.spawnImpulse = ev.impulseWorld;
}
```

El materialize de abajo (`state==Ragdolling && ragdollId==0`) se dispara el mismo tick.

### Sensor bodies (Unity isTrigger / Unreal Overlap)

`PhysicsWorld::createBody` extendida con `bool isSensor = false`. Si true: `BodyCreationSettings::mIsSensor = true` → Jolt detecta contactos pero NO empuja al body que lo atraviesa. Persistido como `RigidBodyComponent::isSensor` + serializado como `is_sensor: true` en `.moodmap`.

Cleanup en transición ragdoll: si la entity tiene `RigidBodyComponent` (proxy hitbox sensor para detectar el impacto), `RagdollSystem` lo `destroyBody` al spawnear el ragdoll — los part-bodies del ragdoll lo reemplazan.

### Tuning publicado

| Param | Default | Setter runtime |
|---|---|---|
| `impactSpeedThreshold` | 4 m/s | `setRagdollImpactSpeedThreshold(f32)` |
| `impactImpulseFactor` | 0.3 (arcade) | `setRagdollImpactFactor(f32)` |

Banshee tuning (en `makeDefaultSA()` + `banshee_sa.moodvehicle`, derivado de docs públicos del `handling.cfg` de GTA SA):

| Param | F2H67 | F2H68 |
|---|---|---|
| `maxTorque` | 500 Nm | **800 Nm** (acelera SA-style) |
| `brakeTorque` | 1500 Nm | **4500 Nm** (frenado snappy, 3× motor) |
| `handbrakeTorque` | 4000 Nm | **6000 Nm** (derrape pronunciado) |

## Cambios fuera del scope inicial

- **Revert del sub-mesh selector polish**. F2H68 intentó agregar `pivotOffset` calculado del AABB de cada sub-mesh + render-side `model * translate(-pivotOffset)` cuando `subMeshName != ""`. Funcionaba para wheels (Kenney exporta wheels con vertices baked al world del modelo) pero rompía el chassis `body` (re-centraba un mesh que ya estaba bien posicionado). **Revertido**: el field `SubMesh::pivotOffset` se quitó. El `vehicle_demo.moodmap` ahora usa 1 entity por vehículo (sin sub-mesh selector por wheel) — pattern Unity/Unreal/GTA estándar: 1 GameObject/Actor por mesh-part.
- **`MeshLoader.cpp` fallback aiNode → aiMesh para `SubMesh::name`**. Anteriormente solo se usaba `aiMesh::mName` (suele ser genérico tipo "Mesh.001" en FBX Kenney). Ahora prioriza el nombre del `aiNode` owner del mesh (nombre semántico que el dev ve en su DCC). Útil aunque no usemos sub-mesh selector para vehículos.

## Bug conocido — NPC no transiciona a Ragdolling al ser embestido

**Reportado por el dev en la validación final del Bloque D2.** Pasos:
1. Spawnar el Banshee + NPC con `RigidBodyComponent` sensor.
2. Subir al auto, acelerar contra el NPC a > 4 m/s.
3. **Observado**: chassis pasa atravesando el NPC sin rebote (sensor body funcionando), pero el NPC NO cae en ragdoll (sigue animado).

**Hipótesis a probar en F2H69:**
- El `OnContactAdded` puede no estar invocándose para Dynamic vs Sensor en Jolt — verificar con un `Log::physics()` temporal.
- `closingSpeed` < threshold por proyección sobre normal incorrecta (la del manifold puede apuntar de manera distinta para sensors).
- El `bodyToEntity` map puede no tener el NPC registrado al momento del impacto — verificar timing del `registerBodyEntity` post-`createBody` para la entity con `is_sensor=true`.
- El drain en `RagdollSystem::tick` puede no estar leyendo la cola si el sistema corre antes que `physicsWorld.step()` ese frame — verificar orden de tick.

**Por qué se cierra F2H68 sin resolverlo:**
- La infra completa (ContactListener + map + sensor + drain) está implementada y testeada en unit tests (6 cases verde).
- El integration test (vehicle vs NPC end-to-end) requiere debug con logs en runtime + posible refactor de orden de tick — scope mejor acotado en hito propio.
- 1029/10227 tests verde, sin regresiones.
