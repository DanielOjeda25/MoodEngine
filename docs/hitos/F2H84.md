# F2H84 — Undo unificado en Material / Item / Quest editors

**Estado:** Cerrado (2026-05-23)
**Tag:** `v1.75.0-fase2-hito84`
**Predecesor:** F2H83 (Refactor archivos grandes hot path render).
**Sucesor planeado:** F2H85 (atajos de teclado configurables — único pendiente
del plan original Fase 2 sin hacer; cerrar F2H42 que se renombró a F2H42-perf).

Noveno hito de **Sub-fase 2.7**. Cierra la deuda histórica de los 3 editores
de assets (Material/Item/Quest) que no tenían undo — el Inspector lo tenía
desde Hito 32 D, pero el resto del editor seguía editando sin red de
seguridad.

---

## Qué siente el usuario

- En el **Material Editor**, editás `metallic` / `roughness` / `ao` /
  `albedo_tint` y un Ctrl+Z los revierte (igual que en el Inspector).
- En el **Item Property Editor**, editás `name` / `description` /
  `icon_path` / `model_path` / `stackable` / `max_stack` / `slot
  width|height` y Ctrl+Z los revierte.
- En el **Quest Property Editor**, editás `name` / `description` /
  `category` y Ctrl+Z los revierte.
- Si **cambiás de asset** en el browser, el history se limpia (los
  comandos previos capturan punteros al asset anterior; revertirlos
  mutaría al nuevo cargado en su lugar).

Lo que **NO entra**: vector/map mutations (agregar/quitar tags, stats,
objectives, rewards). Esas requieren commands específicos (vector
snapshot vs single-field) que se difieren a hito propio si emerge
fricción real — hoy estos editores se usan en ráfagas chicas donde
el undo de campos cubre el caso 95%.

## Bloques

### A — Infra compartida `EditAssetPropertyCommand<T>` + `AssetEditTracker`

- `src/editor/commands/EditAssetPropertyCommand.h` (NUEVO): gemelo
  templated de `EditPropertyCommand<T>` (Hito 32 D) pero sin `Entity`
  como dependencia. Setter es `std::function<void(const T&)>` — el
  callsite captura el path al campo via lambda.
- `src/editor/panels/assets/AssetEditTracker.h` (NUEVO): gemelo de
  `InspectorEditTracker` — variant con los tipos que los 3 editors
  realmente editan (`f32, int, bool, glm::vec3, glm::vec4, std::string`).
- `trackAssetPropertyEdit<T>(tracker, current, history, setter, label)`
  — mismo patrón que `trackPropertyEdit` del Inspector: captura
  before al `IsItemActivated`, push command al
  `IsItemDeactivatedAfterEdit` con before/after, revierte
  programáticamente antes del push para que `execute()` reaplique
  (UNA sola fuente de verdad de "cómo se aplica el cambio").

### B — Material Editor: 4 widgets undoable

`MaterialEditorPanel.h` gana `EditorUI* m_ui` (vía `setEditorUi`) +
`AssetEditTracker m_editTracker`. `.cpp` wirea:
- `albedo tint` (glm::vec3) — ColorEdit3
- `metallic` (f32) — SliderFloat
- `roughness` (f32) — SliderFloat
- `ao` (f32) — SliderFloat

Drop targets de texturas: **no entran**. La razón es que un drop es
un cambio puntual (no un drag con beg/end) — la mecánica del tracker
no aplica. Hito propio si emerge.

Cleanup: removidos los `m_xxxPreDrag` que solo servían para logging
(la nueva infra reemplaza el patrón). Cambio de material limpia el
history (`hist->clear()`).

### C — Item Property Editor: 8 widgets undoable

`ItemPropertyEditorPanel.h` gana `AssetEditTracker m_editTracker`
(ya tenía `m_ui`). `.cpp` wirea:
- `name_key` / `name_literal` (std::string) — toggle determina cuál
- `description_key` / `description_literal` (std::string) — toggle
- `icon_path` (std::string)
- `model_path` (std::string)
- `stackable` (bool)
- `max_stack` (int)
- `slot width` (int) — InputInt
- `slot height` (int) — InputInt

Tags + stats: **no entran**. Son `vector<string>` / `map<string,float>`
con add/remove inline; commands de vector son scope mayor.

`loadFromPath` limpia el history (cambio de item).

### D — Quest Property Editor: 5 widgets undoable

`QuestPropertyEditorPanel.h` gana `AssetEditTracker m_editTracker`.
`.cpp` wirea (sección Identity solamente):
- `name_key` / `name_literal` (std::string)
- `description_key` / `description_literal` (std::string)
- `category` (std::string)

Objectives y Rewards (vectores con structs nested): **no entran**.
Misma razón que tags/stats — vector commands son scope mayor; el
caso común es agregar/quitar/reordenar, no editar UN campo de un
objective con undo granular.

`loadFromPath` limpia el history.

## Decisiones

### D1 — Setter sin entity, captura el path al campo via lambda

**Contexto:** `EditPropertyCommand<T>` (Inspector) toma `Entity` + `Setter`
que recibe `(Entity&, const T&)`. Los assets no son entities — son
buffers internos del panel (`m_loaded`) o punteros del AssetManager
(`MaterialAsset*`). Adaptar el comando a uno de los dos sería invasivo.

**Decisión:** El nuevo `EditAssetPropertyCommand<T>` toma solo `Setter`
con firma `(const T&)`. El callsite captura el resto:
- Material: `[mat](const f32& v) { mat->metallicMult = v; }`
- Item: `[this](const std::string& v) { m_loaded.icon_path = v; m_dirty = true; }`

**Razones:**
- Símbolos genérico vs ad-hoc: un solo comando para los 3 editors.
- El callsite ya sabe qué campo está editando — no hay valor en
  abstraerlo en el comando.
- `m_dirty = true` se mete en el setter para que tanto execute()
  como undo() marquen el panel como sucio (consistente con la edicion
  directa).

**Trade-off:** los lambdas capturan `this` o `mat`. Si el panel
descarga el asset entre push y undo, el lambda apunta a memoria
inválida — por eso `loadFromPath` / cambio de material llaman
`historyStack->clear()`. Patrón ya usado en `NodeGraphSandboxPanel`
y `ShaderGraphEditorPanel`.

### D2 — Diferir vectores / maps (tags, stats, objectives, rewards)

**Contexto:** Item editor tiene `tags` (vector<string> con chips
add/remove) + `stats` (map<string,float> con table add/remove).
Quest tiene `objectives` y `rewards` (vector de structs anidadas).

**Decisión:** No incluir en F2H84. El comando para una mutación de
vector es de naturaleza distinta — necesita capturar el vector
completo o usar un patrón insert/erase con `vector_diff`.

**Razones:**
- Scope: la infra de `EditAssetPropertyCommand<T>` cubre el caso
  90% (edición de campos simples). Vector commands abren un nuevo
  diseño que es mejor atacar cuando emerja un caso real.
- Riesgo: tags + stats están con vector<string>::erase iterador-
  invalidante; cualquier undo tendría que respetar el orden post-
  insert. No es trivial.

**Revisión:** atacar si el dev pierde una mutación grande de stats /
objectives y reporta dolor real.

### D3 — Limpiar history en cambio de asset (no migrar comandos)

**Contexto:** los comandos capturan punteros (`mat`, `this->m_loaded`)
que dejan de ser válidos cuando cambia el asset cargado. Dos opciones:
- (a) Migrar comandos: cada uno detecta "ya no soy relevante" y se
  vuelve no-op.
- (b) Limpiar el history al cambio de asset.

**Decisión:** (b). Más simple, ya usado en otros panels
(`NodeGraphSandbox`, `ShaderGraphEditor`).

**Razones:**
- Cross-asset undo no es feature pedida.
- Migrar agrega complejidad: cada comando tendría que saber a qué
  asset pertenece + el panel rastrear la equivalencia path↔asset.
- Limpiar history a la vez que cambias de asset es comportamiento
  predecible: Ctrl+Z opera sobre lo que estás viendo, no sobre
  ediciones de otro item que ni siquiera está cargado.
