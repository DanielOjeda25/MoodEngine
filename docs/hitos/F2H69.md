# F2H69 — Trigger NPC debug + pipeline glTF multi-node + DeLorean swap

**Estado:** Cerrado (2026-05-19)
**Tag:** `v1.57.0-fase2-hito69`
**Predecesor:** F2H68 (auto-ragdoll por impacto — infra completa con bug conocido).
**Sucesor planeado:** **F2H70** — Vehicle engine fixes sistémicos (auto-spawn-height, quat sync, split-by-node de wheels).

---

## Motivación

F2H68 dejó la infra de auto-ragdoll funcionando en unit tests (6 cases verde) pero el sample end-to-end vehicle vs NPC sensor **no transicionaba a Ragdolling**. Las cuatro hipótesis subordinadas (callback no se dispara para Dynamic vs Sensor, closingSpeed mal proyectada, timing del register, orden de tick) requerían debug con logs en runtime, no más unit tests.

En paralelo, el pipeline de assets visuales arrastraba una deuda: el sedan Kenney `.fbx` cumplía F2H67 pero no permitía iterar con modelos descargados de Sketchfab/CGTrader (formato glTF multi-node con node transforms anidados que el `MeshLoader` no aplicaba — el DeLorean salía gigante o desfasado). F2H69 ataca los dos frentes y reemplaza el modelo del demo por el DeLorean correctamente armado.

## Bloques

### Bloque A — Fix trigger NPC + logs de diagnóstico

**Hipótesis confirmada en runtime con logs:** `JPH::Body::IsSensor()` automáticamente pone `mAllowSleeping = false` solo si el body se crea Dynamic. Los sensores creados Kinematic (caso del NPC: kinematic + `is_sensor: true`) heredan el default `mAllowSleeping = true` y entran a sleep tras ~5s sin movimiento. Cuando el chassis del vehicle los embiste, **Jolt no genera `OnContactAdded`** porque el sensor está dormido (optimización standard del broadphase Jolt: bodies en sleep no producen contactos).

**Fix en `PhysicsWorld::createBody`:** si `isSensor == true` (independiente del MotionType), forzar `BodyCreationSettings::mAllowSleeping = false`. Pattern estándar de Unity/Unreal para triggers permanentes — un sensor que duerme deja de funcionar como trigger.

**Tuning lateral:** `impactSpeedThreshold` bajado de 4.0 a 1.0 m/s. A 4 m/s el dev necesitaba arrancar el auto con throttle pleno desde lejos para activar el trigger; el feel arcade-ish (estilo GTA SA) querido necesita activación a velocidades de maniobra normal. 1.0 m/s evita falsos positivos por contacto inicial pero permite atropellar caminando.

**Logs `[F2H69-DEBUG]` temporales** en `OnContactAdded` (discriminar eventos sub-threshold cuando hay sensor involucrado + log de eventos encolados) + `RagdollSystem::tick` drain (resolución entity, validaciones, transición). Removidos post-validación en este mismo hito (Bloque B cleanup).

### Bloque B — Cleanup logs post-validación

Removidos los `[F2H69-DEBUG]` de `PhysicsWorld_Impact.cpp` (sub-threshold sensor log + ENCOLA log) y `RagdollSystem.cpp` (drain summary + per-event traces + TRANSITION log). El path por defecto vuelve a ser silencioso; reactivable trivialmente si re-emerge un bug similar.

`impactSpeedThreshold = 1.0 m/s` queda como default permanente — el feel arcade-ish está alineado con el tuning de `makeDefaultSA()` (alta tracción + brakes 4500 Nm + handbrake 6000 Nm), y se puede subir runtime con `setRagdollImpactSpeedThreshold(...)` si una escena requiere mayor robustez contra contactos accidentales.

### Bloque C — Pipeline glTF multi-node (consolidation)

**`MeshLoader.cpp` (loader Assimp):** detecta extensión `.gltf` / `.glb` (lowercase comparado) y aplica las **node transforms acumuladas root→owner** (`acc = parent.mTransformation * acc` walking parents) al vertex data:

- **Position:** `p = acc * p_local` por vertex (vec3 → vec3 con homogeneous mat4 multiply).
- **Normal:** `nrm = aiMatrix3x3(acc) * nrm_local`, re-normalizada (la 3x3 mata translation; uniform scale OK).
- **AABB local:** recalculado por submesh tras aplicar la matriz; el AABB global del MeshAsset se expande con los AABBs post-transform.

**FBX intacto:** la convención Kenney/Mixamo trae vertices baked al world del mesh (sin node transforms intermedias que aplicar). Aplicar la matriz acumulada sobre vertices que ya están en world rompería los modelos pre-existentes.

**Sin split-by-node:** el plan original mencionaba opt-in `splitByNode` flag para que cada node con mesh se cargara como `SubMesh` independiente (permitiendo, p. ej., rotar las ruedas del DeLorean separadas del chassis). Decidido en favor de **consolidation** (todos los nodes en 1 MeshAsset con vertices pre-transformados) — alcanza para "1 auto sólido" visual unitario, evita complicar `SceneSerializer` / lookup-by-node-name / wheel-mesh sync con `VehicleConstraint`. El split-by-node real queda como follow-up en F2H70 cuando emerja la demanda concreta (ruedas rotantes visuales independientes).

### Bloque D — DeLorean swap

**Tres deletes previos:**
- `assets/dmc_delorean/{license.txt, scene.bin, scene.gltf, textures/delorean1_baseColor.png}` (DeLorean Sketchfab v1, multi-archivo, unidades 3DS Max mm — incompatible con el nuevo asset pipeline).
- `assets/vehicles/banshee_sa/{License.txt, Textures/colormap.png, banshee_sa.moodvehicle, sedan.fbx}` (Banshee Kenney F2H67, ya no se usa visualmente; el tuning SA-style se mantiene en `VehicleConfig::makeDefaultSA()` en código).

**Nuevo asset:** `assets/vehicles/delorean/delorean.glb` (single-file GLB con texturas embedded, 293 KB) procesado headless con scripts `pygltflib` (no requirió Blender):

1. **`scale_glb.py`** — bake escala uniforme x1.86 a vertex positions + node translations (modelo original 2.27 m → DeLorean DMC-12 real 4.22 m).
2. **`flatten_glb.py`** — bake todas las node matrices al vertex data; detecta nodos con `det(M) < 0` (7 de 17 — wheel2/wheel4/DELOREAN/interior/i_chair2/Box05 mirror baked del export 3DS Max) y reversea winding order + flippea normales para que backface culling vea la cara correcta; node matrices final = identity. Equivalente a "Apply All Transforms" de Blender pero headless.
3. **`center_glb_y.py`** — offset Y a vertex positions para que el origin del modelo quede en su centro vertical (AABB Y simétrico de -0.568 a +0.568 m).

**Verificación headless:** `verify_glb_aabb.py` walking del árbol de nodes con matrices acumuladas confirma dimensiones finales **4.220 × 1.853 × 1.136 m** — match exacto a un DeLorean DMC-12 real.

**`vehicle_demo.moodmap`:**
- `mesh_path` → `vehicles/delorean/delorean.glb`.
- `configPath: ""` → fallback automático a `makeDefaultSA()` (drop del `.moodvehicle` redundante; el tuning vive en código, no en archivo aparte).
- `tag: "DeLorean"`.
- Workarounds residuales asset-specific (a absorber por el engine en F2H70): `position.y = 0.568` (halfHeight del modelo para apoyar en piso), `rotationEuler: [0, 180, 0]` (facing del modelo).

## Pendientes / candidatos F2H70

Identificados en sesión 2026-05-19 al validar visualmente la integración del DeLorean. Los tres son fixes en C++ (engine), no en assets — el principio operacional es que el engine absorba las variaciones del modelo, no el dev a mano en el moodmap.

1. **Auto-spawn-height del chassis.** El VehicleSystem no consulta el AABB del `MeshAsset` asociado al entity al crear el body Jolt → cada modelo requiere `transform.position.y` ajustado al halfHeight visual (asset-specific). Fix: leer AABB del mesh en `VehicleSystem::tick` (al materialize lazy) y aplicar offset Y al `tf.worldMatrix()` que se pasa a `createVehicle`. El moodmap pasaría `position.y = 0` (piso) y el engine se encarga.

2. **Quat sync sin gimbal.** `writeWorldMatrixToTransform` (línea 75 `VehicleSystem.cpp`) usa `glm::extractEulerAngleXYZ` para convertir matriz post-Jolt → euler XYZ → tf.rotationEuler. Esa conversión sufre gimbal lock y devuelve ángulos equivalentes con orden no determinista (180° en Y puede salir como (180,0,180) en vez de (0,180,0)). Al re-aplicar como euler, el resultado visual es otra orientación. Fix: o bien `TransformComponent` con quaternion opcional, o bien `worldMatrix` cached que sobreescriben directo (sin euler en el path principal); euler queda como UI/inspector only.

3. **Split-by-node de wheels.** `MeshLoader` actual consolida los sub-meshes del GLB en uno solo — las ruedas (geometría wheel1/wheel2/wheel3/wheel4 del DeLorean) son fixed dentro del mesh y no rotan visualmente aunque Jolt esté simulando wheel rotation. Fix: opt-in `splitByNode` flag en `loadMesh` que preserva cada node con mesh como `SubMesh` independiente con nombre canónico (`wheel_FL` / `_FR` / `_RL` / `_RR` por convención) + VehicleSystem sincroniza el transform de esos submeshes con `st.wheelWorlds[i]`. Si el modelo no expone wheel meshes con nombres canónicos, fallback al mesh consolidado (modelo legacy).

Cuando F2H70 cierre, el `vehicle_demo.moodmap` se limpia: `position.y = 0`, `rotationEuler = [0, 0, 0]`, y las ruedas rotan visualmente bajo throttle/steer.

## Decisión meta sobre el alcance

El plan original tenía un Bloque C amplio (consolidation + opt-in `splitByNode` + tests roundtrip). Se decidió **consolidation only** durante la implementación, con split-by-node como follow-up F2H70. Razones:

- Consolidation alcanza el goal visual unitario del Bloque D (1 DeLorean entero, sin necesidad de rotar wheels independientes — eso lo simula Jolt sin sync visual).
- Split-by-node implica refactor de `SceneSerializer` (cómo se referencia un sub-mesh: `<gltf_path>#<node_name>`?), del `MeshRendererComponent` (¿múltiples mesh_ids o un MeshAsset con array de SubMeshes nombrados?), y de `VehicleSystem` (cómo encuentra los wheel meshes para sincronizar). Es un hito propio.
- El usuario explicitó durante la sesión que los workarounds asset-specific en el moodmap son síntoma de bug del engine, no del asset — confirmó la dirección sistémica de F2H70.

Trade-off aceptado: ruedas estáticas visualmente en este hito; cabe arreglarse cuando se decida split-by-node como path principal.
